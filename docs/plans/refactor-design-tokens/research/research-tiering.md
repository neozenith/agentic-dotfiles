# Design token tiering & naming: how shipped systems actually do it

Research date 2026-08-30. Every claim carries a source URL; quotes are verbatim from official docs or official source repos. Method note: most of these doc sites are client-rendered, so where the public page returns an empty shell the citation points at the system's own source repo, which is authoritative and machine-checkable.

## 1. Material Design 3 (Google)

- **Tiers: 3 — *reference* / *system* / *component*.** "Each component token maps to a system token, which has a concrete reference value." ([material-web/docs/theming/README.md](https://github.com/material-components/material-web/blob/main/docs/theming/README.md))
- Verbatim definitions (same URL): reference — "Reference tokens hold concrete values, such as a hex color, pixel size, or font family name." system — "System tokens define decisions and roles that give the design system its character, from color and typography, to elevation and shape." component — "Component tokens are design attributes assigned to elements. They can be system tokens or concrete values."
- **Grammar:** `md` · `<tier: ref|sys|comp>` · `<group>` · `<role>`, dash-flattened in CSS. "Tokens follow the naming convention `--md-sys-color-<token>`. All tokens have a corresponding `--md-sys-color-on-<token>` for content color with accessible contrast." ([color.md](https://github.com/material-components/material-web/blob/main/docs/theming/color.md))
- Examples verbatim: `--md-sys-color-primary`, `--md-sys-color-on-primary-container`, `--md-sys-shape-corner-medium`, `--md-ref-typeface-brand`, `--md-filled-button-container-color`.
- **Naming wart worth knowing:** the component tier breaks the prefix pattern — "unlike `--md-ref-*` and `--md-sys-*` tokens, which are prefixed with `ref` and `sys`, component tokens are *not* prefixed with `comp`." (README.md)
- **Modes:** light/dark are two *generated value sets over identical system-token names*, scoped by CSS selector; no mode slot in the name.
- **Strongest published new-role gate of any system here**, verbatim: "Defining custom color roles should be considered only if you cannot achieve your desired colors with other Material color solutions." ([define-new-colors](https://m3.material.io/styles/color/advanced/define-new-colors)) — plus a default-to-no on optional roles: "If you aren't sure whether your product should use the add-on roles, it probably shouldn't and you can ignore them." ([roles](https://m3.material.io/styles/color/roles))
- **And the clearest threshold for minting a component token at all:** "Not every stylistic choice of a component will be able to be expressed as a token, but whenever a design choice applies to multiple components of similar intent, a token should be used." ([overview](https://m3.material.io/foundations/design-tokens/overview))
- **Authored vs generated:** the reference palette and the entire light+dark scheme are *computed* from ≤5 key colours by Material Theme Builder / `material-color-utilities` ("Generated from Material Theme Builder Figma plugin or `material-color-utilities`", color.md). Humans author only the key colours and component overrides. ([m3 overview](https://m3.material.io/foundations/design-tokens/overview))

## 2. Adobe Spectrum

- **Tiers: 3 — *global* / *alias* / *component-specific*** — and the source repo makes the tiering literal, splitting colour into four files whose own descriptions read: `color-palette.json` "Raw color values (hex/rgb) for the Spectrum palette"; `semantic-color-palette.json` "Semantic palette tokens (e.g. semantic blue, semantic red)"; `color-aliases.json` "Semantic color tokens that reference the palette (e.g. focus, overlay)"; `color-component.json` "Component-specific color tokens." ([docs/markdown/tokens](https://github.com/adobe/spectrum-design-data/tree/main/docs/markdown/tokens))
- Examples verbatim: `blue-100` (global, flagged `"private": true`), `accent-color-900` (semantic palette, `$schema: …/alias.json`), `accent-background-color-default` (alias), `action-bar-border-color` (component). ([color-aliases.json](https://github.com/adobe/spectrum-design-data/blob/main/packages/tokens/src/color-aliases.json))
- **Grammar:** dash-delimited with no tier prefix — the *file* carries the tier, the *name* carries `[role]-[property]-[state]` (`accent` + `background-color` + `default`/`hover`/`down`).
- **Modes: a mode axis inside one token.** The canonical shape is a `color-set` whose `sets` key holds `light` / `dark` / `wireframe` siblings under a single name — the cleanest "one name, N modes" model in this survey. Dimension tokens reuse the identical shape with `desktop`/`mobile` scale sets instead of colour modes — verified in [`layout-component.json`](https://github.com/adobe/spectrum-design-data/blob/main/packages/tokens/src/layout-component.json). One `sets` mechanism, two different mode axes: this is the single most reusable idea in the survey.
- **Authored vs generated:** the JSON *is* the human-authored source of truth (every token carries a stable `uuid`); all platform outputs are generated, and CI enforces the schema — "`moon run tokens:validateDesignData` — JSON Schema (Layer 1) + catalog rules (Layer 2)". ([packages/tokens/README.md](https://github.com/adobe/spectrum-design-data/blob/main/packages/tokens/README.md))
- **Names are *generated from a structured name object*, and deviations are tracked as debt** — the most architecturally interesting finding in this survey. `naming-exceptions.json` describes itself as "Legacy token names that cannot be deterministically generated from a structured name object. Each entry tracks a known inconsistency for future remediation", with entries like `gradient-stop-1-avatar` → reason "Legacy name is property-then-component (category: component-ordering); canonical generation order is component-then-property". So Spectrum treats slot *order* as a machine-checkable invariant with an explicit allowlist of violations. ([naming-exceptions.json](https://github.com/adobe/spectrum-design-data/blob/main/packages/tokens/naming-exceptions.json))
- **Governance encoded in semver** (same README): minor = "adding new token / changing a value intentionally / adding deprecation metadata and aliased new tokens where applicable"; major = "deleting tokens / changing token value type". So *adding* a role is cheap and *removing* one is a breaking change — the asymmetry is deliberate.
- **The only NORMATIVE deprecation window found anywhere:** "A deprecated token **MUST** remain in the published dataset for at least **two minor versions** after the version recorded in `lifecycle.deprecatedIn` before it may be removed." Lifecycle is `introduced → active → deprecated → planned removal → removed`, and chained replacements are banned: "Chains of replacements (A replaced by B, B replaced by C) are discouraged; authors should point directly to the final replacement." ([spec/evolution.md](https://github.com/adobe/spectrum-design-data/blob/main/packages/design-data-spec/spec/evolution.md))
- **Spectrum is also the one system that argues *against* semantic naming in places** — worth weighing, since it dissents from the consensus: "Stick with objective (rather than subjective) names. It's very difficult to assign semantic names — which tend to be subjective — to things that have an intended usage." This sits alongside the opposite instruction, "Name for the action, rather than how something looks." ([SPECTRUM_NAMING_GUIDE_WIKI.md](https://github.com/adobe/spectrum-design-data/blob/main/SPECTRUM_NAMING_GUIDE_WIKI.md))

## 3. Salesforce Lightning Design System — the origin

- The term is Salesforce's, and the canonical definition still sits on the SLDS site: design tokens "are the visual design atoms of the design system — specifically, they are named entities that store visual design attributes. We use them in place of hard-coded values (such as hex values for color or pixel values for spacing) in order to maintain a scalable and consistent visual system for UI development." ([lightningdesignsystem.com/design-tokens](https://www.lightningdesignsystem.com/design-tokens/))
- Shopify's own repo credits the lineage: "Design tokens originated at Salesforce" ([polaris-tokens README](https://github.com/Shopify/polaris-tokens/blob/main/README.md)).
- **Tiers:** SLDS 1 is effectively **2** — a flat global token list (`$brand-accessible`, `$brand-background-primary`, `$brand-background-dark`) plus per-component values. Uniquely, every token row publishes governance metadata columns *Released / Themeable / Support*, with the legend "GA Global Access Available to use on the Salesforce Platform. I Internal Available to internal Salesforce developers only. Subject to change." — token-level release phasing, not just tiering. (SLDS URL above)
- Modern SLDS reframes the tiers as **styling hooks and puts the tier in the name**: "Global color styling hooks (--slds-g-*) are predefined values used globally in an app… Component styling hooks (--slds-c-*) enable you to update properties in a specific component." ([LWC dev guide](https://developer.salesforce.com/docs/platform/lwc/guide/create-components-css-custom-properties.html))

## 4. IBM Carbon

- **Carbon does not tier by abstraction at all** — it decomposes orthogonally into *theme / token / role / value*. Verbatim: "**Theme** A theme is a collection of colors designed to create a specific aesthetic. Themes control the color value assigned to a token. For example, Gray 100 theme. **Token** A token is the role-based identifier that assigns a color. Unlike hex codes, tokens apply universally across themes. For example, `$layer`, `$border-subtle`, `$support-error`. **Role** A role is the systematic usage of a color assigned to a token. Roles cannot be changed between themes. **Value** A value is the unique visual attribute (hex code, rgba value) assigned to a token through the use of themes." ([color/overview](https://carbondesignsystem.com/elements/color/overview/))
- The token page's own grouping is **Core Tokens / Component Tokens / AI Tokens** — "Core tokens are global colors that are used across components. They are named and grouped by the common UI element that they are applied to." Groups: Background, Layer, Layer accent, Field, Border, Text, Link, Syntax, Icon, Support, Focus, Miscellaneous. ([color/tokens](https://carbondesignsystem.com/elements/color/tokens/))
- **Grammar, verbatim from Carbon's own migration guide:** "The new naming convention is as follows: `[element] - [role] - [order] - [state]`", with the rationale "All other tokens have been given an adjective descriptor in place of the number ending to help users better understand how a token should be used." ([migrating/guide/design](https://carbondesignsystem.com/migrating/guide/design/#color-tokens)) The overview restates the first two slots: "The first part of the token name references the general UI element the color is being applied to, like `background`, `text`, or `border`. The second part of token name will specify its unique role within the element group like `$border-subtle` or `$text-primary`." Verbatim names: `$layer-01`, `$layer-hover-02`, `$layer-selected-inverse`, `$text-primary`, `$border-subtle-00`, `$background-brand`, `$support-error`. The layering ordinal (`-01/-02/-03`) is a first-class slot no other system here has, and it is documented as a model: "The layering model defines the logic of how colors stack on top of each other in a UI when using the Carbon themes."
- **Modes: separate themes, identical token names.** Four defaults named after their background — White and Gray 10 (light), Gray 90 and Gray 100 (dark). `$background` resolves `#ffffff` in White and `#161616` in Gray 100. No light/dark slot in any name.
- **Published reuse rule** is role-based rather than prohibitive: roles "cannot be changed between themes", which forces a new token whenever a usage must diverge per theme. Component tokens are fenced off — "They are not global tokens like the core tokens and should never be used for anything other than their own component."
- **Carbon publishes NO criteria for when a new semantic token is justified**, and **no standing token-deprecation process** — `/deprecations` covers packages, not tokens. The only lifecycle vocabulary is the one-off v10→v11 change taxonomy (*Updated / Split / New / Deprecated*) plus a compatibility theme "that includes the tokens from v10 and v11 so that you can incrementally update your project." ([docs/migration/v11.md](https://github.com/carbon-design-system/carbon/blob/main/docs/migration/v11.md#design-tokens))

## 5. GitHub Primer

- **Tiers: 3 — `base` / `functional` / `component` (a.k.a. pattern)**, matching the repo layout `src/tokens/{base,functional,component,fallback}`. "This naming convention is broken down into three categories: **base, component/pattern, functional**." ([primer/design token-names.mdx](https://github.com/primer/design/blob/main/content/foundations/primitives/token-names.mdx))
- Verbatim: base — "Base tokens are the lowest level tokens and map directly to a raw value."; functional — "Functional tokens represent global UI patterns."; component — "Component/pattern tokens should only be used in component CSS."
- **Grammar (the most explicitly specified in this survey):** ordered slots `prefix` · `namespace` · `pattern` · `variant` · `property` · `variant` · `scale`, where "the [property] value is always required" and each tier *excludes* specific slots (base excludes pattern/variant; functional excludes namespace/pattern/variant; component excludes namespace). Delimiter is per-platform: "use the `-` dash character for CSS variables and `.` dot character for JavaScript."
- Examples verbatim by tier — base: `base-size-4`, `base-color-green-5`, `base-fontWeight-semibold`; functional: `bgColor-inset`, `borderColor-default`, `boxShadow-inset-thick`; component: `button-primary-bgColor-hover`, `control-danger-borderColor-rest`, `text-codeInline-fontSize`. Shipped values: `--fgColor-default`, `--fgColor-muted`, `--bgColor-accent-emphasis`. ([primitives/color](https://primer.style/foundations/primitives/color))
- **Closed vocabularies for the semantic slots** — the strongest published constraint on inventing new roles: "`default` - The default color variant for a given token… `muted` - The secondary color variant… `emphasis` - The opposite of "muted", emphasis is a stronger color variant", plus fixed scales `xsmall|small|medium|large|xlarge|xxlarge`, `condensed|normal|spacious`, `thin|thick|thicker`, `narrow|regular|wide`. (token-names.mdx)
- **Tier-preference rule, verbatim:** "Component/pattern tokens are used for values that are more specific or unique than functional tokens. These tokens are limited and functional tokens are preferred." And base tokens are locked out entirely: "Base color tokens don't respect color modes and should never be used directly in code or design." ([color-usage](https://primer.style/product/getting-started/foundations/color-usage))
- **Explicit anti-proliferation stance:** "we want to keep the surface area of color variants as small as possible", and "The term `subtle` is being deprecated and replaced with `muted` tokens. This decreases the number of variants we need to maintain" ([ADR-009](https://github.com/primer/primitives/blob/main/contributor-docs/adrs/adr-009-color-token-name-variants.md)). Generalize before specializing: "aim to use a name that is generic enough to influence related components. For example, the pattern `control` can be used for multiple types of controls like buttons, inputs, or interactive action list items."
- **Modes:** `src/tokens/base/color/{light,dark}` — separate value files under identical functional names, plus per-token `org.primer.overrides: { dark: … }` escape hatches. ([src/tokens](https://github.com/primer/primitives/tree/main/src/tokens))
- **Best-in-class rename mechanics:** "When renaming a token, keep the old name as a deprecated alias" — the alias's `$value` points at the new canonical token, `$deprecated` carries the new path, and a removal ledger is mandatory: "When you remove or rename tokens in `src/tokens/`, you **must** document them in `src/tokens/removed.json`… Use `null` for deletions, use the new token path string for renames." ([token-authoring.md](https://github.com/primer/primitives/blob/main/contributor-docs/agents/token-authoring.md), [removed.json](https://github.com/primer/primitives/blob/main/src/tokens/removed.json)) No deprecation *window* is published.
- **Data viz is tokenised at the functional tier**: `functional/color/data-vis.json5` defines `data.<hue>.color.{emphasis,muted}` and carries the anti-reuse rule verbatim: "Use data colors for visualizations only. Do NOT use for semantic meaning (use bgColor.success/danger instead). When using multiple series, ensure sufficient contrast between adjacent colors." ([data-vis.json5](https://github.com/primer/primitives/blob/main/src/tokens/functional/color/data-vis.json5))

## 6. Atlassian Design System

- **Tiers: Atlassian publishes exactly ONE consumer tier.** There is no public primitive layer; every documented token is semantic. The name spec has three slots, verbatim: "**Foundation**: The type of visual design attribute or foundational style, such as color, elevation, or space. **Property**: The UI element the token is being applied to, such as a border, background, shadow, or other property. **Modifier**: Additional details about the token's purpose, such as its color role, emphasis, or interaction state. Not every token has a modifier. For example, `color.text` is our default body text color." ([tokens/design-tokens](https://atlassian.design/foundations/tokens/design-tokens))
- Modifiers decompose into "color role, emphasis level, and interaction state", with emphasis ranging "from subtlest to boldest". ([foundations/color](https://atlassian.design/foundations/color))
- Examples verbatim from the shipped theme artifact: `--ds-text`, `--ds-link`, `--ds-background-neutral`, `--ds-background-success-hovered`, `--ds-background-accent-lime-subtlest-pressed`, `--ds-chart-categorical-1`. ([@atlaskit/tokens atlassian-light](https://cdn.jsdelivr.net/npm/@atlaskit/tokens@16.10.0/dist/cjs/artifacts/themes/atlassian-light.js))
- **Modes: a theme axis applied via data attributes over one CSS-var namespace** — `html[data-color-mode="light"][data-theme~="light:light"]`, so light / dark / increased-contrast / "future" ship as sibling generated stylesheets over identical names. "A theme is a collection of token values designed to achieve a certain look or style… Light mode, dark mode, and high-contrast mode are all examples of theming." (tokens URL)
- **Authored vs generated:** the theme file is machine-written — `THIS FILE WAS CREATED VIA CODEGEN DO NOT MODIFY` / `@codegenCommand yarn build tokens`.
- **Selection rule, verbatim:** "Choose tokens based on meaning where applicable, not specific values… Don't use a token just because the colors appear to match. This can break the experience in other themes." (tokens URL)
- **Deprecation/renaming — the most explicit lifecycle published anywhere in this survey, verbatim:** "lifecycle of `active`, `deprecated`, and `deleted`, eventually being fully removed from the theme (no longer functional). Tokens will be marked as `deprecated` in a minor version, soft-deleted (functional but will raise errors) in the following minor, and deleted in the next `major` release of the tokens library. All breaking changes to APIs and design tokens will be communicated well in advance, with clear cut-off dates for deprecations." Renames are mechanised: the lint rules "have built-in auto-fixers that allow you to update your entire app to the latest tokens automatically via `eslint --fix` and `stylelint "**/*.css" --fix`." ([Forge design tokens and theming](https://developer.atlassian.com/platform/forge/design-tokens-and-theming/))
- **Formal release-phase ladder (5 phases), the most structured in the survey:** "The Atlassian Design System components and foundations (features) have three release phases and two deprecation phases" — Early Access → Beta → General Availability → Intent to Deprecate → Deprecated, with the guarantee "No General Availability feature will be removed from the system without a clearly announced deprecation period." ([release-phases](https://atlassian.design/release-phases))
- **New-token criteria are NOT published** — contribution is closed ("At the moment, we're only accepting contributions from internal Atlassians", [contribution](https://atlassian.design/contribution)). What *is* published is a reuse-vs-new **role test** for accents: "If you aren't sure whether to use an accent token, consider whether the color could be swapped for another without changing the experience or meaning behind it… Don't use accent tokens when the color has a specific meaning in our system, such as information, warning, or success." ([color/accents](https://atlassian.design/foundations/color/accents))
- **And a notable "leave it untokenized" escape hatch:** "if no appropriate token exists for a specific value that must be retained, it is preferable to leave the value unchanged (without converting it to a token) rather than adding it as a fallback." ([use-tokens-in-code](https://atlassian.design/foundations/tokens/use-tokens-in-code))
- **Categorical chart colours are first-class semantic tokens:** `--ds-chart-categorical-1` … `-8`, each with a `-hovered` sibling, alongside role-named chart tokens (`--ds-chart-danger-bold`, `--ds-chart-discovery-bold`, `--ds-chart-brand`).

## 7. Shopify Polaris (brief)

⚠️ `Shopify/polaris` is archived and `polaris.shopify.com/*` now 301s to shopify.dev; the v12-era docs remain published at `shopify.github.io/polaris-react-archive/`, cited below.

- **Tiers: 2 — *palette/primitive* (private) and *alias/semantic* (public).** Verbatim: "The palette tokens which are private and used to create new aliases and the alias tokens which is what designers and developers use" / "These tokens are not available to use directly." ([version-11-color](https://shopify.github.io/polaris-react-archive/previous-releases/version-11-color))
- **The clearest reuse-vs-new fallback rule in the survey**, verbatim: "These tokens should only be used for that explicit purpose. **When no semantic token seems to fit your need, use a primitive token instead.**" Do: "Always use semantic tokens over primitive ones when possible." ([layout-tokens](https://shopify.github.io/polaris-react-archive/design/layout/layout-tokens))
- Role coverage is *deliberately incomplete* — "not all tokens are defined for each color role… Roles like `critical` or `information` will only have a selection of tokens defined" ([palettes-and-roles](https://shopify.github.io/polaris-react-archive/design/colors/palettes-and-roles)) — and new roles are centrally governed: "The creation of new color roles is tied to the Shopify admin." ([using-color](https://shopify.github.io/polaris-react-archive/design/colors/using-color))
- **Intent-in-the-name is explicit:** "Each color token follows the same naming convention. **The purpose and intent of a color token is built into the name itself.**" (version-11-color)
- **Grammar, verbatim from the spec file:** top level `--p-[token-group-name]-[token-name]`; colour specifically `--p-color-[element]-[role?]-[prominence?]-[state?]`, with a second "specialty" form `--p-color-[specialty]-[variant?]-[default-token-structure]`. Examples verbatim: `--p-color-text`, `--p-color-text-secondary`, `--p-color-input-text-tertiary`, `--p-space-100`, `--p-shadow-button-hover`. ([polaris-tokens-structure.md](https://github.com/Shopify/polaris/blob/main/polaris-tokens/polaris-tokens-structure.md))
- Polaris calls the third slot **prominence** where Primer says *variant/emphasis* and Atlassian says *emphasis* — one concept, three words. No categorical data-viz tokens.

## 8. Radix Themes (brief)

- **Tiers: 2, but the semantic layer is an *ordinal scale with published per-step use-cases*, not role names.** "There are 12 steps in each scale. Each step was designed for at least one specific use case" — 1 App background, 2 Subtle background, 3 UI element background, 4 Hovered UI element background, 5 Active/Selected, 6 Subtle borders and separators, 7 UI element border and focus rings, 8 Hovered UI element border, 9 Solid backgrounds, 10 Hovered solid backgrounds, 11 Low-contrast text, 12 High-contrast text. ([understanding-the-scale](https://www.radix-ui.com/colors/docs/palette-composition/understanding-the-scale))
- The only *role aliases* are `accent` and `gray`, remapped per theme: `--accent-1` … `--accent-12` plus `--accent-surface`, `--accent-indicator`, `--accent-track`, `--accent-contrast`; likewise `--gray-*` and `--focus-1..12`. ([themes/docs/theme/color](https://www.radix-ui.com/themes/docs/theme/color))
- **Modes:** every scale ships "light, dark and alpha variants", swapped under the theme wrapper — one name, mode-dependent value. No categorical data-viz tokens.

## 9. Tailwind v4 `@theme` (brief)

- **Tiers: 1, deliberately.** There is no semantic layer — theme variables *are* the primitives and they double as the utility-class generator: "Theme variables are special CSS variables defined using the `@theme` directive that influence which utility classes exist in your project… Theme variables aren't just CSS variables — they also instruct Tailwind to create new utility classes that you can use in your HTML." ([tailwindcss.com/docs/theme](https://tailwindcss.com/docs/theme))
- **Grammar: `--<namespace>-<name>`**, namespace drawn from a closed set that maps 1:1 to a utility API — `--color-*`, `--font-*`, `--text-*`, `--font-weight-*`, `--tracking-*`, `--leading-*`, `--breakpoint-*`, `--container-*`, `--spacing-*`, `--radius-*`, `--shadow-*`, `--ease-*`, `--animate-*`. Examples verbatim: `--color-mint-500: oklch(0.72 0.11 178)`, `--breakpoint-3xl: 120rem`, `--font-poppins: Poppins, sans-serif`.
- **Architecturally load-bearing constraint:** "Theme variables are also required to be defined top-level and not nested under other selectors or media queries" — a mode axis *inside* `@theme` is structurally impossible; dark mode is done with the `dark:` variant over ordinary CSS vars, outside `@theme`.

# Synthesis

## Q1. Is there consensus on tier count and tier names?

**On the count: yes — three is the centre of gravity.** Material (reference/system/component), Spectrum (global/alias/component) and Primer (base/functional/component) agree on three. **On the names: no consensus whatsoever — there is no shared word for any of the three tiers.**

Where they genuinely disagree:

1. **Which tiers consumers may touch.** This is the real fault line, not the count. Spectrum ships a full component tier and treats alias as the recommended consumption layer; Primer says component tokens "should only be used in component CSS"; Atlassian publishes *no* component tier; Tailwind publishes *no* semantic tier.
2. **Whether primitives are public.** Spectrum marks palette entries `"private": true`; Material Web does not even support `--md-ref-palette`; Atlassian exposes no primitives at all. Tailwind inverts this completely — the primitives *are* the public API.
3. **The axis of decomposition.** Carbon does not tier by abstraction; it decomposes into theme/token/role/value, which is orthogonal. Radix replaces role names with a 12-step ordinal scale carrying documented use-cases.
4. **Whether the tier is encoded in the name.** Material (`md.sys.`), SLDS (`--slds-g-`/`--slds-c-`) and Primer (`base-`) put the tier in the string; Spectrum, Carbon, Atlassian and Polaris put it in the file/group and keep names clean.
5. **How many middle layers.** Spectrum is the only system with **two**: a *semantic palette* (`accent-color-900` — "which blue is our accent") between the raw palette and *aliases* (`accent-background-color-default` — "what this colour is for"). If brand-mapping must be separable from usage-mapping, Spectrum is the precedent.

## Q2. What do they call the layer between raw values and component usage?

| Term | Used by |
|---|---|
| **system** | Material Design 3 (`md.sys.*`) |
| **alias** | Adobe Spectrum (`color-aliases.json`; schema type is literally `alias`) |
| **functional** | GitHub Primer (`src/tokens/functional/`) |
| **semantic** (a.k.a. **alias**) | Shopify Polaris — uses both words for the same public layer, over a private *palette* tier; also Spectrum, for its *semantic-color-palette*, one rung lower than its aliases |
| **role / role-based** | IBM Carbon — "A token is the role-based identifier that assigns a color" |
| **styling hook** | Salesforce SLDS 2 (`--slds-g-*` global hooks) |
| **step** (ordinal, use-case documented) | Radix Colors |
| **(unnamed — it is the only layer)** | Atlassian; slots are *foundation / property / modifier* |
| **theme variable** | Tailwind v4 — explicitly *no* middle layer at all |

Nobody in this survey uses "decision" as a tier name, despite its currency in blog-level writing. For a new system: **"semantic" is the most widely understood** (Polaris, Spectrum, DTCG community), **"alias" is the most precise** — it names the mechanism (a reference to another token) rather than an aspiration. Avoid "system" and "functional": both are already overloaded in most codebases.

## Q3. Do any treat categorical / qualitative data colours as part of the token system?

**Three of nine do, and where they do, the placement is consistent: the semantic/functional tier, never the primitive tier, and always with an explicit prohibition against reuse for UI meaning.**

- **Atlassian — yes, first-class semantic tokens.** `--ds-chart-categorical-1` … `-8`, each with a `-hovered` state sibling, in the same namespace and same generated theme artifact as `--ds-text`. It also ships *role*-named chart tokens (`--ds-chart-danger-bold`, `--ds-chart-discovery-bold`, `--ds-chart-brand`), i.e. it models qualitative-by-index **and** qualitative-by-meaning as separate sets.
- **GitHub Primer — yes, at the functional tier.** `functional/color/data-vis.json5`, shaped `data.<hue>.color.{emphasis,muted}`, with the published usage rule "Emphasis variants are for lines, bars, and borders. Muted variants are for area fills and backgrounds… Do NOT use for semantic meaning (use bgColor.success/danger instead)."
- **IBM Carbon — yes, but deliberately outside the core token set.** The guidance frames them as *palettes* with an ordering contract — "Categorical (or qualitative) palettes are best when you want to distinguish discrete categories of data that do not have an inherent correlation. The colors of this palette should be applied in sequence strictly as described below. The sequence is carefully curated to maximize contrast between neighboring colors" ([data-visualization/color-palettes](https://carbondesignsystem.com/data-visualization/color-palettes/)) — and tokenises them in the separate `@carbon/charts` package as `--cds-charts-<group-size>-<option>-<index>` (e.g. `--cds-charts-14-1-3`, `--cds-charts-1-1-1-hovered`). The group-size slot encodes "the right palette when you know you have exactly N series" — a nuance nobody else has.
- **No: Material 3, Spectrum, Polaris, Radix, Tailwind.** `md.sys.color` has no chart-series role; Spectrum's four colour files contain no categorical set; Radix leaves series colour to the consumer picking hues off the 12-step scales.

The transferable lesson: categorical colour is **not** a primitive — the ordering and the contrast-between-neighbours guarantee *are* the design decision, so it belongs at the semantic tier — and it needs an explicit anti-reuse rule, because index-named tokens otherwise get grabbed as generic accents.

## Cross-cutting: published rules for when a new semantic role is justified

**No system publishes a full create-vs-reuse decision tree.** The two closest are Material's "only if you cannot achieve it otherwise" and Polaris's "fall back to a primitive". Everything else is procedural.

| System | New-role criteria | Deprecation process |
|---|---|---|
| **Material 3** | **Strongest** — "considered only if you cannot achieve your desired colors with other Material color solutions"; token-worthy when "a design choice applies to multiple components of similar intent" | **None standing** — one blog-announced instance ("Both methods will co-exist for an extended transition period") |
| **Polaris** | **Clearest fallback** — "When no semantic token seems to fit your need, use a primitive token instead" | Explicit token checklist: deprecate in a minor, automate the migration, remove in the next major |
| **Primer** | Partial — "functional tokens are preferred", "keep the surface area of color variants as small as possible", closed slot vocabularies | **Strongest mechanics** — deprecated alias + mandatory `removed.json` ledger; no window |
| **Spectrum** | Partial — scope rule only (does the meaning generalize across components, or is it one component's identity?) | **Only NORMATIVE window** — MUST survive ≥2 minor versions |
| **Atlassian** | **Not published** (contribution closed); only a role test for accents | **Strongest phase ladder** (5 phases) + `eslint --fix` codemods; window not numeric |
| **Carbon** | **None published** | **None standing** — only a v10→v11 taxonomy + compatibility theme |

Three transferable mechanisms, in rough order of leverage:

1. **A closed slot vocabulary** (Primer): fix `default|muted|emphasis`, `thin|thick|thicker` etc. and make `property` mandatory, so a proposed role must express itself in existing slot values or it is out of spec. This is the cheapest possible governance — it rejects bad proposals without a meeting.
2. **A semver cost asymmetry** (Spectrum, Polaris): adding is a minor, removing is a major. Combined with Spectrum's normative "≥2 minor versions" window, this makes addition cheap and *reversal* predictable, which is what actually lets a team decide quickly.
3. **An automated rename path** (Atlassian's auto-fixers, Primer's `removed.json`, Polaris's "create automated migration(s)"): the real constraint on inventing roles is the cost of being wrong. Every system that mints roles freely has invested in codemods first.

The consistent *usage*-side rule, stated in near-identical words by four systems, is name-and-choose-by-meaning: Atlassian "Choose tokens based on meaning where applicable, not specific values… Don't use a token just because the colors appear to match"; Polaris "The purpose and intent of a color token is built into the name itself"; Carbon "Tokens are role-based"; Material "named for how or where it's used". **Spectrum is the sole dissenter**, warning that "semantic names… tend to be subjective" and preferring objective names where intent is contested — worth taking seriously rather than dismissing, because it is the only system here whose names are machine-generated from a structured object and therefore has to defend every slot.
